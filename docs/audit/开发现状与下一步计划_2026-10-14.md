## 三、关键缺口与风险

只列影响继续开发或最终交付的问题。

1. **诊断结果没有存进系统。** M4 的循环是「诊断 → 候选 → 实验 → 判断」，第一环现在只是 docs 目录里的文件，循环没法据此判断「是不是提示词的问题，要不要停」。这是 M4 的硬前置。
2. **核心旅程没在真实数据上跑通过。** 真实库里标注为 0，所以以下几条都只在单测里出现过：
   - 实验评判里的「人工标注」维度；
   - 「标对的字段被改坏」这种退化；
   - 按 §0.3 的实施闸门，M2 的「一个字段错误 → 根因报告」也还没真正过关。
3. **网页 API 没有鉴权，而且可能对局域网开放。** 「采纳候选」这类不可撤销的操作，任何能访问 3000 端口的人或进程都能调用。M4 一旦让 Agent 自动跑循环，Agent 只要有 shell 就能绕过人工审批。
4. **评测基准不稳定。**
   - 没有 Gold 版本，也没有 holdout。自动循环会拿同一批标注反复迭代，容易「对着答案改提示词」。
   - 硬规则没有版本号，规则一改，历史判定就漂移。
5. **预算单位有问题。** §11.3 要求「最大费用」，但服务商不返回价格，`estimated_cost` 一直是空的，没法按金额控制。
6. **运维层面的小隐患。**
   - `data/e2e.db` 已经 478MB，测试越跑越慢。
   - 环境里的模型超时设成 120 秒：大模型 `qwen3.8-max` 在 10-14 已因 `MODEL_TIMEOUT` 失败一次，而代码默认值是 300 秒。
   - 需求文档 `Prompt_Studio_v1.3md.md` 还没提交进仓库。
   - 业务待决的 4 项（M0 §6）至今未决。

## 六、当前最优先的 3 件事

1. **A1 服务只监听本机**（10 分钟）。现在任何能访问 3000 端口的人都能采纳候选、改动正式提示词，而这一步不可撤销；后面让 Agent 自动循环之前必须先堵上。改动一行，几乎没有风险。
2. **B1 到 B4 诊断会话落库**。这是 M4 循环的第一环，也是 §8 唯一整块缺失的部分。不做它，自动优化没有依据判断「该不该改提示词」，只能退化成盲目试错，正是需求明确禁止的「把所有问题都归因于 Prompt」。
3. **C1、C2 用真实错误字段做一次贯通验收**。按需求 §0.3 的实施闸门，M2 的首验条件（一个字段错误 → 有来源的根因报告）还没在真实错误上满足过；真实库里标注为 0，实验评判里的「人工标注」维度也从没在真实数据上用过。先证明这条链路，再在它上面加循环。
